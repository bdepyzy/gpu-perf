What You Need Before Starting

Hardware

  • NVIDIA B200 / GB200-class GPU (compute capability 10.0; verify with nvidia-smi -q) is the only execution target
  • For multi-GPU work, use B200 GPUs within the same node or B200 cluster allocation; record the exact topology
  • CUDA Toolkit 13.x preferred; 12.8 minimum for B200/CUTLASS
  • ≥ 128 GB system RAM and ≥ 500 GB free NVMe storage

Software to Install

  • ncu, nsys, compute-sanitizer, cuobjdump, and nvdisasm
  • Python 3.12+, torch, triton, nvidia-cutlass-dsl, pytest, and hypothesis
  • nccl-tests; vLLM/SGLang source builds only when Cycle 4 needs production trace context
  • cutlass, flash-attn, and PyTorch C++/CUDA extension tooling

Accounts & Access

  • GitHub account and a public kernel-lab repository
  • GPU MODE Discord plus access to an externally scored NVIDIA kernel problem or hackathon
  • Reliable B200 access for benchmark reproduction and, during multi-GPU weeks, a B200 allocation with recorded topology
  • Optional blog/static site; the repository and four anchor reports are the portfolio

Mindset Prep

  • One hypothesis and one controlled change per kernel version
  • Preserve failures, counterexamples, and regressions
  • Use SASS as evidence, not as an annotation-volume contest
  • Protect 7–8 hours of sleep; skill compounds only if the schedule survives all 12 weeks

Work Blocks: A Menu, Not Four Daily Obligations

The detailed day cards are a playbook. Required work is the orange/green implementation-and-evidence path plus a small set of cycle acceptance gates. Blue reading and purple packaging tasks are pulled in when the active hypothesis needs them. Sunday is a short audit/recovery window; every fourth Sunday is completely off.

HARDS Implementation 3–4h

Write the smallest correct B200 kernel, then change one mechanism at a time. Move among CUDA C++, Triton, CuTe DSL, inline PTX, and framework integration only when the comparison answers a concrete question.

MEAS Measurement & Correctness 2–3h

Correctness matrix, sanitizer runs, benchmarks, profiles, and realistic SOL calculations. Write the hypothesis and failure criterion before every run. A fast kernel with a race, unsupported tail shape, or cherry-picked baseline does not count.

READ Read & Predict on demand

Read the exact docs, source, paper, or worklog needed to unblock the next experiment. End with one mechanism summary and one prediction; reading without a changed experiment is optional reference work.

BUILD Integration & Evidence at cycle gates

Package kernels behind PyTorch-callable interfaces, add tests and fallbacks, update the harness, and write results when the cycle requires it. Preserve meaningful and failed versions; polish only the four anchor artifacts.

Implement → measure → falsify → version → integrate → expose to review  |  stop at the cycle gate or a documented plateau

Operating Rules

Source ladder

Primary docs and source first: NVIDIA Blackwell/CUDA, Triton, CUTLASS/CuTe DSL, PyTorch, vLLM/SGLang, and NCCL/NVSHMEM. Papers second. Worklogs such as gau-nernst's are studied for experimental method, then verified on B200 against NVIDIA source, documentation, and measurements.

Measurement contract

Every result row needs: exact GPU, driver, CUDA version, commit hash, clock/power state, input shape, warmup count, repetitions, median/p95, and the Nsight metrics used. If any field is missing, the number is not publishable.

Correctness and sanitizer contract

Before optimization, freeze a trusted reference and test tiny, odd, non-multiple, large, strided, and deliberately misaligned shapes where the interface permits them. Cover relevant NaN/Inf and precision cases. CUDA kernels must pass compute-sanitizer memcheck plus racecheck/synccheck where applicable; framework operators must have a documented fallback for unsupported inputs.

Version-ladder contract

Name variants v0 through vN. Each version changes one hypothesis, records correctness and performance, and explains the generated-code or trace delta. The final table includes regressions and neutral results, not only the winner.

External-pressure contract

Every two-week cycle ends with some outside pressure: a fixed evaluator, technical reviewer, public reproducer, or upstream issue. Cycle 4 must use an untouched fixed evaluator, and the capstone must survive external review. Keep messy submissions and attribution.

Evidence and publication contract

Every cycle ends with a defensible evidence packet, but only four outputs receive portfolio-level polish: the memory/microbenchmark study, cross-stack packaged operator, B200 multi-GPU kernel, and integrated capstone. Weekly notes stay concise and internal unless they reveal something unusually useful.

Priority contract

Required gates define completion. Optional tasks are pulled in when the hypothesis needs them. Stretch tasks are explicitly expendable. Do not complete optional work while a required correctness, measurement, integration, or external-review gate is open.

Guidance format

Every checkbox gets a collapsible Why / How note. Treat these as method prompts, not answer keys: they should tell you how to think, what evidence to collect, and which questions to ask before you claim success.

Distributed Systems Track

One-node collective roofline

Measure all-reduce, reduce-scatter, all-gather, broadcast, point-to-point, and all-to-all over 1 KB to multi-GB messages. Compare effective bandwidth to NVLink/PCIe topology from nvidia-smi topo -m. Keep separate curves for latency regime, bandwidth regime, and protocol transition points.

Serving parallelism map

Know what each scheme spends communication on: DDP all-reduces gradients; FSDP/distributed optimizer trades memory for reduce-scatter and all-gather; tensor parallelism inserts collectives inside layers; pipeline parallelism creates bubbles; sequence/context parallelism moves activation shards; MoE expert parallelism adds all-to-all and load balance risk.

Overlap target

The practical distributed question is not "how fast is NCCL?" but "how much communication is exposed on the critical path?" Every distributed profile should report exposed communication time, overlapped communication time, rank skew, and the layer or bucket where overlap breaks.

Week 12 Completion Checklist

Cross-Cutting Daily Habits

1. Correctness and sanitizers gate every performance number

Reference → adversarial fixtures → sanitizer → benchmark. Inspect PTX/SASS after a source, compiler, or counter hypothesis requires it; generated code is evidence, not a ritual performed before the kernel is known correct.

2. Every profiler capture answers a written question

Start with the smallest metric set that can falsify the hypothesis, then widen to memory workload, source counters, warp states, or instructions. Full profiles are expensive and often obscure the actual question.

3. Every source changes an experiment or a code path

Summarize the mechanism, methodology, verified claim, open assumption, and one experiment or source location it changes. Reading without a resulting prediction does not count as kernel work.

4. Every week the work meets outside pressure

Publish a reproducible version, request technical review, submit to a fixed evaluator, or prepare a focused upstream issue/patch. Optimize for useful criticism and an auditable trail, not posting volume.

5. Track every result in one machine-readable registry

ColumnDescription
Result IDStable kernel/operator + shape/dtype/layout + implementation version
EnvironmentGPU/architecture, clocks, driver, toolkit, framework/compiler commits
CorrectnessOracle, tolerance, adversarial suite, sanitizer status, unsupported cases
MeasurementMedian/p95, variance, compile/dispatch cost, warmup and repetitions
BoundMeasured bandwidth/compute/latency bound and percent achieved
BaselineLibrary/framework/external evaluator version and result
ProvenanceCommit, exact command, raw files, hypothesis, decision, and limitations

Key Terms

SASS — Streaming Assembler. The actual machine code that runs on the GPU. Below PTX, architecture-specific.

PTX — Parallel Thread Execution. Virtual ISA that nvcc compiles to. SASS is generated from PTX by ptxas.

Triton — A Python kernel language and compiler for expressing blocked GPU programs. Its value here is both fast kernel development and a compiler pipeline you can inspect and challenge.

TTIR / TTGIR — Triton’s target-independent and GPU-oriented intermediate representations. Together with LLVM IR, PTX, and SASS, they reveal where source intent changes during lowering.

NVRTC — NVIDIA Runtime Compilation. Compiles CUDA C++ source to PTX at runtime, enabling justified shape/dtype/architecture specialization with an explicit cache.

TMEM — Tensor Memory. Blackwell-specific on-chip memory that tensor cores write MMA results into. Not registers, not shared memory — its own space.

TMA — Tensor Memory Accelerator. A dedicated hardware unit (Hopper+) that does async bulk copies between global and shared memory independently of warps.

CTA — Cooperative Thread Array. The CUDA term for a thread block. The unit of scheduling on an SM.

SM — Streaming Multiprocessor. The GPU core that executes warps.

Warp — 32 threads executing in lockstep. The fundamental unit of execution.

MFU — Model FLOPS Utilization. Achieved training FLOPS / GPU peak FLOPS for the precision in use.

cuBLAS — NVIDIA's closed-source BLAS library. The performance gold standard for matrix multiply on NVIDIA GPUs.

CUTLASS — NVIDIA's open-source template library for writing high-performance GEMM kernels. The reference implementation for modern GPU matmul.

CuTe — CUTLASS's tensor layout algebra. The abstraction layer for expressing data layouts and tiling strategies.

CuTe DSL — NVIDIA CUTLASS's Python DSL for expressing CUDA kernels with CuTe layouts, tensors, and code generation while staying close enough to inspect generated PTX/SASS.

SOL / speed of light — The best applicable measured bound for the operation on the actual system: bandwidth, compute, latency, or communication. Prefer it to an unattainable marketing peak.

Symmetric memory — Peer-accessible allocations with matching virtual-address/layout assumptions across ranks, used by some GPU-driven communication designs. Allocation symmetry alone does not define ordering.

Acquire / release — Memory-ordering semantics used to publish payloads and observe readiness flags. Correct scope and ownership are part of the algorithm, especially across GPUs.

tcgen05 — Blackwell's tensor-core PTX instruction family. Replaces Hopper's wgmma for Blackwell tensor-core operations.

mbarrier — Memory barrier. Used for synchronization between async operations and warps. Foundation of producer-consumer pipelines.

ILP — Instruction-Level Parallelism. The amount of independent work a thread can issue without waiting.
